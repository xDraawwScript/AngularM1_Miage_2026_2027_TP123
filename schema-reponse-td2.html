2. L'intercepteur JWT et l'attribut src

auth.interceptor.ts n'intervient que sur les requêtes qui passent par le HttpClient d'Angular : c'est un maillon du pipeline HTTP d'Angular, câblé une seule fois dans main.ts via provideHttpClient(withInterceptors([authInterceptor])).

Une URL posée directement dans un attribut src (par ex. <audio src="http://localhost:3000/api/tracks/123/audio">) n'est jamais chargée par ce pipeline : c'est le navigateur lui-même qui déclenche une requête HTTP native dès qu'il rencontre cet attribut dans le DOM, complètement en dehors du code Angular. L'intercepteur ne s'exécute donc pas, et aucun header personnalisé (comme Authorization: Bearer ...) n'est ajouté.

Conséquence directe : une piste protégée par JWT ne peut pas être lue avec une URL API directement dans src — elle recevrait un 401. D'où le détour obligatoire par HttpClient (pour bénéficier de l'intercepteur) → Blob → URL.createObjectURL(), qui produit une URL locale de type blob:... que le navigateur peut lire nativement, sans nouvelle requête réseau.

Manque identifié : le frontend actuel n'effectue aucune vérification avant l'appel HTTP (ni sur le format du fichier, ni sur sa taille) — il envoie systématiquement la requête et attend la réponse du serveur pour savoir si elle est valide.

Pourquoi la validation frontend ne remplace jamais la validation backend

La validation frontend améliore l'expérience utilisateur : retour instantané, pas d'attente réseau inutile pour une erreur évidente (mauvais format, fichier trop lourd). Mais elle ne remplace jamais la validation serveur, car le frontend est entièrement sous le contrôle de l'utilisateur : il peut être contourné (DevTools, requête curl ou Postman directement vers l'API, un autre client que l'application Angular). Le serveur est le seul endroit qu'un attaquant ne contrôle pas — c'est donc la seule barrière réellement fiable.

4. Questions mémoire, buffering et streaming

Le backend envoie-t-il le fichier entier en mémoire ou peut-il l'envoyer progressivement depuis le disque ?
Il l'envoie progressivement depuis le disque. La route GET /api/tracks/:id/audio utilise res.sendFile(audioPath, callback) (Express), qui lit le fichier en flux (stream) directement depuis le disque vers la réponse HTTP, sans jamais charger l'intégralité du fichier en mémoire vive du serveur.
Avec HttpClient et responseType: "blob", à quel moment le composant reçoit-il généralement le fichier ?
Seulement une fois le téléchargement intégralement terminé. L'Observable retourné par HttpClient n'émet sa valeur (next(blob)) qu'après réception complète de la réponse et assemblage en un objet Blob unique — pas de flux progressif exploitable par défaut (il faudrait reportProgress: true et écouter les événements HttpEventType.DownloadProgress pour un retour intermédiaire, mais le Blob complet n'arrive de toute façon qu'à la fin).
Si la bibliothèque contient 100 morceaux, les 100 fichiers audio sont-ils chargés en mémoire dès l'affichage de la liste ? Justifier à partir du code.
Non. load() (l'affichage de la liste) n'appelle que GET /api/tracks?page=...&limit=..., qui renvoie uniquement des métadonnées (titre, nom de fichier, taille, date) — jamais le contenu binaire. Le Blob audio n'est récupéré que lorsque l'utilisateur clique sur le bouton de lecture d'une piste précise (play(track) → service.audio(track.id)). De plus, audioUrl est un signal unique (pas un tableau) : chaque nouvelle lecture révoque l'URL précédente avant d'en créer une nouvelle, donc jamais plus d'un Blob actif à la fois, quel que soit le nombre de pistes dans la bibliothèque.
Quelle différence y aurait-il avec 100 éléments <audio> utilisant directement une URL HTTP ?
Deux problèmes majeurs. D'abord l'authentification : comme expliqué en section 2, une URL API posée directement dans src ne passe pas par l'intercepteur JWT — chaque requête échouerait avec un 401. Ensuite la charge réseau : même en supposant l'authentification résolue autrement, le navigateur pourrait déclencher jusqu'à 100 requêtes HTTP simultanées ou en attente (selon l'attribut preload de chaque balise), contre une seule requête authentifiée à la fois, déclenchée à la demande explicite de l'utilisateur, dans l'approche actuelle.
Pourquoi l'URL créée par URL.createObjectURL doit-elle être révoquée ?
Parce qu'elle maintient le Blob sous-jacent vivant en mémoire tant qu'elle n'est pas explicitement révoquée via URL.revokeObjectURL(url) — même si l'élément <audio> qui l'utilisait a été retiré du DOM ou que l'utilisateur a changé de page. Sans révocation, chaque nouvelle lecture accumule un Blob supplémentaire en mémoire (fuite mémoire progressive), ce qui peut dégrader les performances, voire faire planter l'onglet sur une session longue avec beaucoup d'écoutes successives.
