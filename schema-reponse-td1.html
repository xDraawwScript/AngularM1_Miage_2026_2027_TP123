TP1 — Guitar Practice Cloud

Mission 0 : cartographie de l'application, schéma du flux de connexion, et rôle de chaque fichier (backend + frontend)

1. Architecture générale

Le flux de données suit toujours le même chemin, jamais l'inverse :

composant Angular → service Angular → HttpClient → API Express → MongoDB

Angular ne parle jamais directement à MongoDB. Le seul point de contact avec la base de données est le backend Express, via des requêtes HTTP passées par un proxy de développement (proxy.conf.json).

Toutes les prochaines requêtes passeront par authInterceptor avec le header Authorization: Bearer <token>
Point clé : l'intercepteur ne fait pas la différence entre route publique et protégée — il ajoute toujours le header s'il existe un token. C'est le authGuard qui empêche d'atteindre une page protégée sans être connecté, et le middleware auth côté backend qui rejetterait (401) une requête sans JWT valide.

4. Backend (backend/) — Express + MongoDB

C'est le serveur : il reçoit des requêtes HTTP, parle à MongoDB, renvoie du JSON. Il ne connaît rien d'Angular.

FichierRôleContenu
src/server.js Point de démarrage réel Se connecte à MongoDB Atlas, crée le compte démo s'il n'existe pas encore, puis ouvre le port d'écoute (3000)
src/app.js Cœur de l'API : toutes les routes et règles métier Fonction createApp() : middlewares (CORS, JSON, logs), fonction token() qui fabrique un JWT, middleware auth qui le vérifie, config Multer pour l'upload, et les 8 routes (health, register, login, users/me ×2, tracks ×3), plus un gestionnaire d'erreurs central
src/models/User.js Forme d'un utilisateur en base Schéma Mongoose (name, email, passwordHash) ; hache le mot de passe avec bcrypt avant sauvegarde ; méthode toPublic() qui ne renvoie jamais le hash
src/models/Track.js Forme d'une piste audio en base Schéma Mongoose (titre, propriétaire, nom du fichier stocké, taille…) ; toPublic() cache le nom technique du fichier sur disque
package.json Dépendances et scripts express (serveur HTTP), mongoose (MongoDB), bcryptjs (hash des mots de passe), jsonwebtoken (JWT), multer (upload fichiers), cors
.env Secrets locaux (jamais commités) MONGODB_URI, JWT_SECRET, PORT
test/api.test.js Tests automatisés Vérifie que les routes répondent comme prévu, sans passer par un vrai navigateur
Idée clé : app.js ne démarre pas le serveur lui-même (pas de .listen()) — c'est server.js qui appelle createApp() et ouvre le port. Cette séparation permet aux tests d'utiliser l'application sans réellement écouter sur un port réseau.

6. Réponses aux questions du sujet (Mission 1)

Assistant IA utilisé

Modèle : Claude Sonnet 5 (identifiant claude-sonnet-5), utilisé via Claude Code (l'agent en ligne de commande d'Anthropic).

Suivre sa consommation de tokens :

  • Dans Claude Code : la commande /cost affiche le coût et les tokens consommés pour la session en cours.
  • Sur claude.ai (abonnement Pro/Max) : Paramètres → Usage affiche la consommation par période.
  • En utilisant l'API directement (facturée au token) : le tableau de bord Usage sur console.anthropic.com donne le détail par modèle, avec le coût en dollars.

Qui conseille le meilleur modèle pour une tâche ? Il n'y a pas d'IA « conseillère » universelle intégrée : c'est un choix humain, guidé par la documentation officielle d'Anthropic (docs.claude.com), qui compare les modèles sur la vitesse, le coût et la capacité de raisonnement, et éventuellement par l'enseignant du TP selon le contexte pédagogique. En pratique, le compromis est : un modèle léger (Haiku) pour des tâches simples et répétitives, un modèle intermédiaire (Sonnet) pour du développement applicatif classique comme ce TP, un modèle plus puissant (Opus) pour du raisonnement complexe ou une architecture critique.

Où s'effectue la mise à jour du profil utilisateur ?

Côté frontend :

  • profile-page.html : le formulaire (formControlName="name") et (ngSubmit)="save()"
  • profile-page.ts : la méthode save() lit le formulaire et appelle le service
  • shared/services/auth.service.ts : la méthode update(name) envoie PUT /api/users/me puis met à jour le signal currentUser

Côté backend :

  • backend/src/app.js : la route app.put("/api/users/me", auth, ...) — le middleware auth vérifie d'abord le JWT, puis le handler appelle User.findByIdAndUpdate(req.auth.sub, { $set: { name: req.body?.name } }, ...)
  • backend/src/models/User.js : le schéma Mongoose valide le nouveau nom (minlength) et toPublic() formate la réponse renvoyée

7. Signal vs localStorage

Les deux servent à « retenir » l'état de connexion, mais à des niveaux différents :

  • Le Signal (token, currentUser dans AuthService) vit en mémoire, dans le JavaScript de la page en cours. Il est réactif : dès qu'il change, tous les templates qui le lisent (auth.token(), auth.currentUser()) se remettent à jour automatiquement, sans code supplémentaire. Il disparaît dès que l'onglet est fermé ou la page rechargée.
  • localStorage est un stockage brut du navigateur, non réactif : lire sa valeur ne déclenche jamais de mise à jour de l'interface. Il n'est pas effacé au rechargement de la page — c'est justement ce qui permet de rester connecté après un F5.

Les deux sont utilisés ensemble et se complètent : au démarrage de l'app, token = signal(localStorage.getItem('gpc_token')) relit la valeur persistée pour initialiser le Signal. Ensuite, chaque connexion/déconnexion écrit dans les deux à la fois (storeAuthentication() et logout() dans auth.service.ts) : le Signal pour que l'interface réagisse tout de suite, localStorage pour que la session survive à un rechargement.
